# Accessibility — WCAG AA baseline

The viewer and portal target **WCAG 2.1 AA**. This doc records what is locked
in automation, what is enforced by human review, and where the inventories
live, so a new icon button or modal can not regress the contract silently.
A11y splits across surfaces:

- **Automated** — an [`axe-core`](https://github.com/dequelabs/axe-core-npm/tree/develop/packages/playwright) Playwright-BDD scan
  gates the viewer shell, the annotation sidebar, and every composer dialog at
  Critical / Serious WCAG A + AA findings.
- **Human-enforced** — keyboard navigation, focus-ring policy, ARIA-label
  inventory, and screen-reader smoke are tracked in tables below. The
  inventory is the review checklist when a new interactive element ships.
- **AA contrast** of the `--anno-*` tokens is locked by a separate JSDOM
  values test — methodology and ratios live in [`05-theming.md`](./05-theming.md).

NFR-5 closes when all three sections pass.

## Automated axe baseline

[`../features/nfr-a11y/a11y-baseline.feature`](../features/nfr-a11y/a11y-baseline.feature)
plus [`../features/steps/a11y.steps.ts`](../features/steps/a11y.steps.ts) scan
five surfaces against the `wcag2a`, `wcag2aa`, `wcag21a`, and `wcag21aa` tag
sets and assert zero **Critical** or **Serious** findings:

- the viewer shell (plan mode)
- the inline comment composer dialog (selection-anchored)
- the annotation sidebar with one annotation persisted (annotate mode)
- the Settings menu
- the global comment composer dialog (annotate mode)

**Minor** and **Moderate** violations are recorded in the attached JSON but
do not fail the scan. They are listed in the run output for triage; once a
moderate count climbs, file a follow-up.

### Running

```sh
bun run test:e2e
```

`bddgen` regenerates `.features-generated/` from the new feature file and
Playwright executes the five scenarios against the per-worker viewers booted by
the `viewers` fixture (see [`08-testing.md`](./08-testing.md#parallel-bdd-execution)). On
failure the step attaches an `axe-results` JSON to the test report — the
file lists every violation with its `id`, `impact`, `help`, and the failing
nodes. Open the attachment via the Playwright HTML report or read the JSON
directly in `playwright-report/data/`.

### Coverage interaction

[`../features/support/bdd.ts`](../features/support/bdd.ts) attaches an
`autoCoverage` fixture that runs `page.coverage.startJSCoverage` / `stopJSCoverage`
around every test. `@axe-core/playwright` injects its `axe.min.js` blob into
the page during `.analyze()`, so the JSCoverage payload for a11y scenarios
includes ~80 KB of axe-core script that is _not_ repo source. The
`monocart-coverage-reports` pipeline only resolves source maps emitted by the
viewer's Vite build, so the extra blob drops out of the aggregated report —
it does not perturb repo line coverage.

## Keyboard navigation checklist

Run on macOS Chrome at the test viewport (1280×800) with the reference plan
loaded.

| Step                                          | Expected focus target                                                                                                              |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Reload the page                               | the editor root (the first contentEditable region) holds focus                                                                     |
| Tab                                           | the floating "Approve" / "Request changes" button in the top bar                                                                   |
| Tab                                           | the Settings button (`top-bar-settings`)                                                                                           |
| Shift+Tab loops back                          | reaches `top-bar-brand` before wrapping                                                                                            |
| Open the Settings menu (Enter on the trigger) | menu opens with focus on the first radio item (pointer-open highlights none); Esc closes and returns focus to the Settings trigger |
| Select text in the editor, then press `c`     | inline composer opens, focus on `composer-textarea`; Esc returns focus to the editor with the selection restored                   |
| Press `c` outside a selection (annotate mode) | global composer opens, focus on `global-composer-textarea`                                                                         |
| In any composer                               | Enter saves, Esc cancels — neither bubbles to the page-level hotkeys                                                               |
| `Mod+Enter` outside the editor                | Approve / Submit feedback fires (`useReviewHotkeys`)                                                                               |
| `Mod+Enter` inside an open composer           | suppressed — composer-textarea Enter takes precedence                                                                              |

Hotkeys are owned by
[`../apps/viewer/src/client/hooks/useReviewHotkeys.ts`](../apps/viewer/src/client/hooks/useReviewHotkeys.ts).
Add a row to this table when a new hotkey or focus-target lands.

## Focus-ring policy

Every interactive component must show a visible focus ring on
`:focus-visible` — keyboard focus only, never pointer focus. The baseline
is set in [`../packages/symbiot-ui/src/components/Button.tsx`](../packages/symbiot-ui/src/components/Button.tsx) (line 8):

```text
focus-visible:ring-2 focus-visible:ring-ring focus-visible:outline-none
```

Every shadcn-derived primitive in `@symbiot/ui` (`Button`, `Badge`, `Input`,
`Textarea`, `ScrollArea`, `Tabs`, `Sheet` close, `SidebarMenu`,
`SidebarSection`) inherits the same `ring-2 ring-ring`
pattern; the sidebar variants substitute `ring-sidebar-ring` so the ring
contrasts against the sidebar surface. The token `--ring` lives in
[`../packages/tailwind-config/theme.css`](../packages/tailwind-config/theme.css)
and resolves to a high-contrast value in both themes.

Any deviation from this baseline must be justified inline with a comment.

## ARIA-label inventory

Every icon-only button — i.e. one whose visible content is an icon alone, no
text — must expose an accessible name. The axe baseline asserts label
_presence_; this table is the review check on label _wording_. The testid
column doubles as a partial selector inventory — the full Playwright-BDD
selector rule lives in
[`08-testing.md` § Playwright-BDD selectors](./08-testing.md#playwright-bdd-selectors).

> **Adding an icon-only button?** Append a row here in the same PR. The axe
> baseline can not tell good wording from bad — without the inventory there
> is no review check on the text screen-readers actually announce.

## Screen-reader smoke

Run on macOS VoiceOver (Cmd+F5 to toggle) on the viewer at the reference
plan. Required for every release.

### Comment flow

1. Reload the viewer. VoiceOver announces the document and lands on the
   editor.
2. Use VO+Right to traverse the prose, stop on "quick brown fox".
3. VO+Shift+M to open the rotor, navigate to the floating toolbar's
   "Comment" button — VoiceOver should announce "Comment, button".
4. Press the button. The composer opens — VoiceOver announces the dialog
   title ("Comment on selection") even though it's `sr-only`, then the
   description, then lands on the textarea.
5. Type a body, press Enter. The composer closes; VoiceOver should
   announce the page region returning to the editor.

### Delete flow

1. With one annotation in the sidebar, Tab to the sidebar entry row.
   VoiceOver announces "<kind>, <line range>, <primary>, button" plus the
   row's drift-bg if any.
2. Tab once more to reach the remove action — VoiceOver announces "Remove
   annotation, button".
3. Press Enter. The AlertDialog opens. VoiceOver announces "Remove this
   annotation?" + the kind-specific description.
4. Tab to "Remove" and press Enter. Dialog closes; VoiceOver returns to
   the sidebar list.

Record any deviation (silent surface, wrong order, missing announcement)
in the release notes for the cut and file an issue.

## AA-contrast cross-reference

Annotation hue contrast is verified at the **token** level, not at the
rendered level. The check lives next to the token file:

- [`../packages/tailwind-config/contrast.test.ts`](../packages/tailwind-config/contrast.test.ts) — JSDOM-backed
  Vitest suite that resolves the annotation, typography, and surface tokens —
  and their text-on-surface pairs — in both themes and asserts ≥ 4.5:1 (WCAG AA
  for normal-weight text).
- [`./05-theming.md`](./05-theming.md) — chosen OKLCH values, hex equivalents,
  measured ratios, and the relative-luminance methodology.

Why a separate test from the axe scan: the JSDOM check is a _values_ check
(does the cascade resolve to the right hex), so a browser is overkill.
`axe-core`'s `color-contrast` rule fires at the rendered-element level —
that is the right tool when the prose itself fails contrast, not when the
token cascade does. Both run; neither replaces the other.

## Reduced motion

The app honors the OS "reduce motion" preference (WCAG 2.1 §2.3.3 Animation from
Interactions). The policy follows the common reduced-motion guidance — keep the
opacity/colour transitions that aid comprehension, drop the motion that moves or
scales elements:

- The shadcn surfaces (Dialog, DropdownMenu, Sheet, Tooltip, Popover) animate via
  the `tw-animate-css` `enter`/`exit` keyframes, which compose movement from the
  `--tw-{enter,exit}-translate-*` / `-scale` / `-rotate` / `-blur` vars and fade
  from `--tw-{enter,exit}-opacity`. Under `prefers-reduced-motion: reduce` the
  transform/blur vars are reset to their neutral values, so the surfaces still
  cross-fade in and out but no longer fly, zoom, or spin.
- The decorative SVG icon hovers (the check draw-in and the send plane/trail) are
  pure movement, so they are switched off entirely.

The rule lives at the foot of
[`../packages/tailwind-config/theme.css`](../packages/tailwind-config/theme.css)
so every consumer of the shared theme inherits it. Verify by enabling "reduce
motion" at the OS level (or Chrome DevTools → Rendering → Emulate CSS
`prefers-reduced-motion`) and confirming overlays fade without transform motion.
